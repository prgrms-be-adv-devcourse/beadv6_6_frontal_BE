# Auction 동시성 제어 설계 회의록

## 1. 회의 개요

| 항목 | 내용 |
|---|---|
| 일자 | 2026-07-27 |
| 대상 도메인 | Auction |
| 주제 | 동시 입찰과 경매 종료 시 데이터 정합성을 보장할 방법 검토 |
| 검토 범위 | 비관적 락, 낙관적 락, 조건부 UPDATE, 메시지 큐 직렬화 및 보조 대안 |
| 문서 상태 | 설계 제안 — 구현 전 팀 합의 필요 |

## 2. 결론 요약

현재 구현은 입찰 시 Auction 행에 비관적 락을 사용하고 있어, 동일 경매에 입찰이 집중되는 상황에서는 낙관적 락으로 즉시 교체하는 것보다 현재 방식을 보완하는 편이 안전하다.

우선 적용할 안은 다음과 같다.

1. 입찰, 판매자 즉시 종료, 종료 스케줄러가 모두 동일한 Auction 행 잠금 규칙을 사용한다.
2. 경매 상태뿐 아니라 서버 시각 기준 `endsAt`도 잠금 획득 후 다시 검증한다.
3. 잠금 구간을 짧게 유지하고 WebSocket 발행은 DB 커밋 이후로 이동한다.
4. 종료 스케줄러는 경매별 독립 트랜잭션으로 처리한다.
5. 관심 수 변경은 입찰과 같은 Auction 행을 갱신하지 않도록 분리한다.
6. 위 구조를 안정화한 뒤 k6 결과를 기준으로 낙관적 락 또는 조건부 UPDATE 도입을 결정한다.

`@Version` 기반 낙관적 락은 유효한 대안이지만, 버전 불일치가 발생하면 같은 트랜잭션 안에서 저장만 다시 시도해서는 안 된다. 실패한 트랜잭션 전체를 끝내고 새로운 트랜잭션에서 Auction을 다시 읽어 모든 조건을 재검증해야 한다.

## 3. 현재 구현 분석

### 3.1 입찰 처리

현재 `BidService.placeBid()`는 다음 순서로 동작한다.

1. Auction을 일반 조회하여 1차 검증한다.
2. `findByIdForUpdate()`로 Auction 행에 `PESSIMISTIC_WRITE` 락을 건다.
3. 최신 현재가를 기준으로 2차 검증한다.
4. Bid 이력을 저장한다.
5. Auction의 현재가, 최고 입찰자, 입찰 수를 갱신한다.
6. WebSocket 메시지를 발행한다.
7. 트랜잭션이 커밋된다.

동일 경매 입찰은 DB 행 잠금 획득 순서대로 직렬화되므로 현재가 유실 갱신을 막을 수 있다. 다만 WebSocket 발행이 커밋 전이면 이후 DB 롤백 시 클라이언트가 존재하지 않는 입찰을 먼저 볼 수 있다.

### 3.2 잠금 규칙이 적용되지 않은 변경 경로

Auction 상태를 바꾸는 모든 코드가 동일한 락 규칙을 사용하지는 않는다.

- 판매자 즉시 종료는 일반 조회 후 Auction을 종료한다.
- 종료 스케줄러는 만료된 LIVE Auction 목록을 조회한 뒤 순차 종료한다.
- 관심 등록/취소는 Auction의 `watcherCount`를 직접 증감한다.

따라서 입찰과 종료가 동시에 실행되거나, 향후 Auction Pod가 여러 개로 늘어날 경우 다음 문제가 발생할 수 있다.

- 종료 직전 입찰이 저장됐지만 낙찰자 계산에는 반영되지 않는 경우
- 경매가 종료된 뒤 입찰이 승인되는 경우
- 여러 스케줄러가 같은 경매 종료 이벤트를 중복 생성하는 경우
- 관심 수 변경과 입찰이 같은 Auction 행을 서로 덮어쓰는 경우

### 3.3 종료 시각 검증

경매 상태가 `LIVE`이더라도 `endsAt`이 이미 지났고 스케줄러가 아직 상태를 변경하지 못했을 수 있다. 따라서 입찰 승인 조건은 `status == LIVE`만으로 충분하지 않다.

```text
입찰 가능 = status가 LIVE이고 DB 또는 서버 기준 현재 시각이 endsAt보다 이전
```

잠금 획득 후 이 조건을 다시 검사해야 한다. 여러 서버를 운영할 때 애플리케이션 시계 차이를 줄이려면 DB 시각을 조건부 UPDATE에 사용하는 방법도 고려한다.

## 4. 반드시 지켜야 할 정합성 규칙

어떤 동시성 제어 방식을 선택하더라도 다음 조건은 변하지 않는다.

1. 승인된 입찰은 `LIVE` 상태이고 종료 시각 전이어야 한다.
2. 입찰가는 직전 확정 현재가에 최소 입찰 증가액을 더한 값 이상이어야 한다.
3. Bid 이력 저장과 Auction 현재가 갱신은 하나의 DB 트랜잭션에서 함께 성공하거나 함께 실패해야 한다.
4. Auction의 `currentBid`, `currentBidderId`, `bidCount`는 승인된 Bid 이력과 일치해야 한다.
5. 경매 종료와 신규 입찰은 한 가지 순서로만 확정되어야 한다.
6. 낙찰자와 낙찰가는 마지막으로 승인된 최고 입찰과 일치해야 한다.
7. 외부 메시지는 DB 커밋에 성공한 상태만 전달해야 한다.
8. 클라이언트나 네트워크 재시도로 같은 입찰이 중복 저장되지 않아야 한다.

동시에 도착한 요청의 공정성 기준도 명시해야 한다. 현재 DB 락 방식의 확정 순서는 클라이언트가 버튼을 누른 시각이 아니라 서버가 DB 잠금을 획득하고 커밋한 순서이다.

## 5. 대안 A — 비관적 락 보완

### 5.1 설계

입찰뿐 아니라 Auction의 가격 또는 상태를 바꾸는 모든 경로가 같은 행을 `SELECT ... FOR UPDATE`로 잠근다.

```text
요청 수신
  -> 짧은 사전 검증
  -> Auction 행 잠금
  -> 상태·종료 시각·현재가 재검증
  -> Bid와 Auction 저장 또는 Auction 종료
  -> 커밋
  -> WebSocket 등 외부 알림
```

적용 대상은 다음과 같다.

- 신규 입찰
- 판매자 즉시 종료
- 스케줄러 자동 종료
- 관리 작업 중 Auction 가격이나 상태를 변경하는 기능

### 5.2 종료 스케줄러 개선

스케줄러 전체 목록을 하나의 긴 트랜잭션으로 처리하지 않는다.

1. 종료 후보 ID를 제한된 개수로 조회한다.
2. 각 Auction ID를 별도의 `REQUIRES_NEW` 트랜잭션으로 처리한다.
3. 해당 행을 잠근 뒤 상태와 종료 시각을 재검증한다.
4. 이미 다른 인스턴스가 종료했다면 정상적인 중복 시도로 보고 건너뛴다.

이렇게 하면 한 건의 실패로 전체 종료 작업이 롤백되거나 많은 행의 잠금이 오래 유지되는 문제를 줄일 수 있다.

### 5.3 잠금 실패 처리

- DB 락 대기 시간에 상한을 둔다.
- 락 타임아웃은 시스템 장애와 구분되는 오류 코드로 변환한다.
- 서버에서 비관적 락 요청을 무제한 재시도하지 않는다.
- 동일 트랜잭션에서 여러 행을 잠가야 한다면 항상 같은 순서로 잠가 교착 상태 가능성을 낮춘다.

### 5.4 장단점

| 장점 | 단점 |
|---|---|
| 현재 코드 변화가 가장 작다 | 경합 시 요청이 대기한다 |
| 인기 경매처럼 동일 행 충돌이 많은 경우에도 재시도 폭증이 없다 | 대기 중 DB 연결을 점유한다 |
| 입찰 승인 순서를 설명하기 쉽다 | 긴 트랜잭션은 지연과 교착 가능성을 키운다 |
| 단일 DB 트랜잭션으로 강한 정합성을 유지한다 | 모든 변경 경로가 잠금 규칙을 지켜야 한다 |

### 5.5 판단

현재 규모와 구현 상태에서 가장 현실적인 1차안이다. 단, 입찰 경로 한 곳에만 락을 거는 것은 불충분하며 종료 경로까지 같은 규칙으로 묶어야 한다.

## 6. 대안 B — `@Version` 낙관적 락

### 6.1 기본 설계

Auction 엔티티에 버전 컬럼을 추가한다.

```java
@Version
@Column(name = "version", nullable = false)
private Long version;
```

```sql
ALTER TABLE auction
    ADD COLUMN IF NOT EXISTS version BIGINT NOT NULL DEFAULT 0;
```

JPA는 갱신 시 읽었던 버전을 조건에 포함하고 성공하면 버전을 증가시킨다.

```sql
UPDATE auction
SET current_bid = ?, current_bidder_id = ?, bid_count = ?, version = version + 1
WHERE auction_id = ? AND version = ?;
```

영향받은 행이 0건이면 다른 트랜잭션이 먼저 Auction을 변경한 것이다. 이때 `OptimisticLockException` 또는 Spring의 `ObjectOptimisticLockingFailureException` 계열 예외가 발생할 수 있다.

### 6.2 버전 불일치 시 올바른 처리

버전 충돌이 발생한 트랜잭션은 롤백 대상으로 취급해야 한다. 다음과 같이 같은 트랜잭션에서 `save()`만 반복하면 안 된다.

```text
잘못된 방식: 예외 catch -> 동일 엔티티 save 재호출
```

올바른 재시도 단위는 입찰 업무 전체이다.

```text
BidRetryFacade                 // 트랜잭션 없음
  -> BidAttemptService.placeOnce()  // 새로운 트랜잭션
       -> Auction 다시 조회
       -> 상태·종료 시각·금액 다시 검증
       -> Bid 저장
       -> Auction 갱신
       -> flush/commit
```

권장 재시도 정책은 다음과 같다.

- 최대 2~3회
- 10~50ms 범위의 지수 백오프와 jitter
- 전체 재시도 시간 예산 200~500ms
- 매 시도마다 최신 Auction을 다시 읽고 모든 업무 규칙을 재검증
- 재시도 한도를 넘으면 `409 Conflict`와 최신 현재가·최소 입찰가를 반환

충돌 예외는 flush 또는 커밋 시점에 나타날 수 있다. 시도 내부에서 실패를 명확히 감지해야 한다면 `saveAndFlush()` 또는 `EntityManager.flush()`를 사용하되, 외부 재시도 계층과 내부 트랜잭션 계층을 분리해야 한다. 같은 클래스의 내부 메서드 호출로 트랜잭션 프록시가 우회되지 않도록 별도 Bean으로 구성한다.

### 6.3 재시도 중 업무 결과가 달라지는 경우

첫 시도에서 유효했던 입찰도 재조회 후에는 다음 이유로 거절될 수 있다.

- 다른 입찰로 최소 입찰가가 올라감
- 판매자 또는 스케줄러가 경매를 종료함
- 종료 시각이 지남

이는 재시도 실패가 아니라 최신 상태에 따른 정상적인 업무 거절이다. 서버가 사용자 입력 금액을 임의로 올려 재입찰해서는 안 된다.

### 6.4 관심 수와의 거짓 경합

현재 `watcherCount`도 Auction 엔티티에 있어 관심 등록/취소가 Auction 버전을 증가시킨다. 그대로 `@Version`을 도입하면 가격과 무관한 관심 수 변경 때문에 입찰이 충돌할 수 있다.

낙관적 락을 적용하기 전에 다음 중 하나가 필요하다.

- 관심 수를 `auction_watch_stats` 같은 별도 테이블로 분리
- Redis를 기준으로 계산하고 DB에는 비동기 집계
- 별도 원자적 카운터 UPDATE를 사용하되 Auction 버전과 분리

가격·상태 정합성을 보호하는 버전과 조회용 통계의 변경 주기를 분리하는 것이 권장된다.

### 6.5 장단점

| 장점 | 단점 |
|---|---|
| 충돌이 적을 때 DB 락 대기 시간이 짧다 | 인기 경매에서는 충돌과 전체 트랜잭션 재시도가 증가한다 |
| 누락된 JPA 변경 경로도 버전으로 감지할 수 있다 | 재시도 계층과 예외 매핑이 복잡해진다 |
| 여러 Pod에서도 별도 분산 락 없이 동작한다 | 같은 행의 조회용 통계도 거짓 충돌을 만든다 |
| 충돌을 명시적으로 관측할 수 있다 | 클라이언트가 보는 지연 편차가 커질 수 있다 |

### 6.6 판단

일반 경매의 충돌률이 낮다면 좋은 선택이다. 그러나 종료 직전 인기 경매처럼 하나의 행에 쓰기가 집중되면 비관적 락보다 많은 작업을 반복할 수 있다. 현재 `watcherCount`를 분리하지 않은 채 즉시 적용하는 것은 권장하지 않는다.

## 7. 대안 C — 조건부 원자 UPDATE

### 7.1 설계

업무 조건을 UPDATE의 WHERE 절에 포함해 한 문장으로 현재가를 선점한다.

```sql
UPDATE auction
SET current_bid = :amount,
    current_bidder_id = :bidderId,
    bid_count = bid_count + 1,
    version = version + 1
WHERE auction_id = :auctionId
  AND status = 'LIVE'
  AND ends_at > CURRENT_TIMESTAMP
  AND :amount >= current_bid + min_increment
RETURNING current_bid, current_bidder_id, bid_count, version;
```

- 1행 갱신: 해당 금액의 입찰 선점 성공
- 0행 갱신: 경매 종료, 낮은 금액 또는 동시 변경 중 하나이므로 최신 상태를 재조회해 결과를 구분

Auction 갱신과 Bid 삽입은 반드시 같은 DB 트랜잭션에서 실행한다. Bid 삽입이 실패하면 앞선 UPDATE도 롤백되어야 한다.

### 7.2 주의점

- PostgreSQL 전용 SQL 또는 JDBC/native repository가 필요하다.
- JPA 영속성 컨텍스트에 이미 로드된 Auction이 있으면 갱신 후 clear 또는 refresh가 필요하다.
- `@Version`과 병행할 경우 모든 native UPDATE가 version을 증가시켜야 한다.
- 판매자 종료와 스케줄러 종료도 `status = 'LIVE'` 같은 조건부 UPDATE 또는 동일 행 락을 사용해야 한다.
- UPDATE 성공 후 알림은 여전히 커밋 이후에 전송해야 한다.

### 7.3 장단점

| 장점 | 단점 |
|---|---|
| DB 왕복과 애플리케이션 잠금 보유 구간이 짧다 | 도메인 로직 일부가 SQL로 이동한다 |
| 낮은 입찰과 종료 후 입찰을 DB에서 원자적으로 거절한다 | 실패 원인을 알려면 재조회가 필요하다 |
| 높은 경합에서도 애플리케이션 전체 재시도를 줄일 수 있다 | PostgreSQL 의존성이 커진다 |
| 다중 Pod 환경에서도 동작한다 | JPA와 native SQL 혼용 규칙이 필요하다 |

### 7.4 판단

k6 결과에서 락 대기 또는 낙관적 충돌이 병목으로 확인될 경우 가장 유력한 고성능 개선안이다. 현재 코드보다 변경 범위가 크므로 테스트 근거 없이 먼저 도입하지 않는다.

## 8. 대안 D — 경매별 메시지 큐 직렬화

입찰 명령을 Kafka 등에 넣고 `auctionId`를 파티션 키로 사용하면 동일 경매의 명령이 한 소비자에서 순서대로 처리된다.

```text
API -> 입찰 명령 저장/발행 -> auctionId 파티션 -> 단일 순서 처리 -> 결과 통지
```

필수 설계 요소는 다음과 같다.

- API가 `202 Accepted`를 반환할지 결과를 기다릴지 결정
- 요청별 idempotency key
- 중복 소비 방지 또는 멱등 처리
- consumer lag 제한과 모니터링
- 실패 명령 재처리 및 DLQ
- 처리 결과를 WebSocket 또는 조회 API로 전달

순간적인 대량 입찰을 흡수할 수 있지만 응답 모델과 운영 구조가 크게 달라진다. 극단적인 트래픽이 실측되기 전에는 장기 대안으로 둔다.

## 9. 기타 대안

### 9.1 Redis 분산 락

Redis 락만으로 최종 정합성을 보장하는 방식은 권장하지 않는다. 락 임대 만료, 네트워크 분리, 프로세스 일시 정지 시 두 작업이 동시에 락을 소유한 것처럼 동작할 수 있다. 사용하더라도 DB 버전 또는 조건부 UPDATE를 최종 방어선으로 두고 fencing token까지 설계해야 한다.

### 9.2 PostgreSQL Advisory Lock

`pg_advisory_xact_lock()`으로 경매 ID별 잠금을 만들 수 있으나 키 매핑, DB 종속성, 운영 가시성이 추가된다. 이미 잠글 Auction 행이 존재하므로 현재는 행 잠금보다 명확한 이점이 없다.

### 9.3 SERIALIZABLE 격리 수준

직렬화 이상을 DB가 감지해 트랜잭션을 중단시키는 방법이다. 중단된 전체 트랜잭션 재시도가 필요하고 범위가 넓어 단일 Auction 행 정합성 문제에는 비용이 크다. 기본 선택으로 사용하지 않는다.

## 10. 대안 비교

| 방식 | 낮은 경합 | 높은 경합 | 구현 복잡도 | 응답 특성 | 현재 적합도 |
|---|---:|---:|---:|---|---:|
| 보완된 비관적 락 | 좋음 | 좋음, 대기 증가 | 낮음 | 순차 대기 | 가장 높음 |
| `@Version` 낙관적 락 | 매우 좋음 | 재시도 증가 | 중간 | 충돌 시 재시도/409 | 조건부 적합 |
| 조건부 원자 UPDATE | 매우 좋음 | 좋음 | 중간~높음 | 짧은 처리, 실패 후 재조회 | 성능 개선 후보 |
| 경매별 메시지 큐 | 좋음 | 매우 좋음 | 매우 높음 | 비동기 또는 대기 | 장기 대안 |
| Redis 분산 락 단독 | 보통 | 운영 위험 | 높음 | 임대 시간 영향 | 비권장 |
| SERIALIZABLE | 보통 | 재시도 증가 | 중간 | 트랜잭션 중단 가능 | 비권장 |

## 11. 권장 단계별 설계

### 11.1 1단계 — 현재 비관적 락의 정합성 완성

- 입찰, 판매자 종료, 스케줄러 종료에 같은 Auction 행 잠금 적용
- 잠금 후 `status`, `endsAt`, 현재가 재검증
- 종료 후보를 경매별 독립 트랜잭션으로 처리
- WebSocket을 `AFTER_COMMIT`으로 이동
- Kafka는 기존 Transactional Outbox 유지
- 락 대기 시간과 타임아웃 메트릭 추가
- 관심 수의 Redis/DB 갱신 실패 시 복구 정책 정리

### 11.2 2단계 — 변경 빈도가 다른 데이터 분리

- `watcherCount`를 Auction 가격·상태 행에서 분리
- 입찰 요청에 idempotency key 도입
- 동일 키 재요청은 새 Bid를 만들지 않고 기존 결과 반환
- 경매 종료 이벤트의 event ID에 유일성 제약 또는 멱등 소비 적용

### 11.3 3단계 — `@Version` 안전망 검토

관심 수 분리 후 Auction에 version을 추가한다. 비관적 락을 유지한 상태에서도 잠금 없이 변경되는 경로를 탐지하는 안전망으로 먼저 운영할 수 있다. 이후 k6에서 충돌률이 충분히 낮으면 입찰 경로를 낙관적 락으로 전환한다.

### 11.4 4단계 — 실측에 따른 최종 선택

초기 판단 기준은 다음과 같이 제안한다. 수치는 절대 기준이 아니라 동일한 AWS 환경에서 여러 번 측정해 조정한다.

| 관측 결과 | 선택 후보 |
|---|---|
| 낙관적 충돌률 1~3% 이하, p95 안정 | 낙관적 락 + 제한 재시도 |
| 인기 경매 충돌률 5~10% 이상 | 비관적 락 유지 또는 조건부 UPDATE |
| DB 락 대기가 주된 병목 | 조건부 UPDATE 실험 |
| 단일 경매 순간 요청이 DB 처리량을 지속 초과 | 경매별 큐 직렬화 검토 |

## 12. 오류 응답과 클라이언트 처리

권장 오류 구분은 다음과 같다.

| 상황 | HTTP 예시 | 처리 |
|---|---:|---|
| 버전 충돌 후 서버 재시도 소진 | 409 | 최신 현재가와 최소 입찰가 반환 |
| 잠금 대기 시간 초과 | 409 또는 503 | 경합과 DB 장애를 구분해 정책 결정 |
| 최신 가격보다 낮은 입찰 | 409 | 최신 가격 표시 후 사용자 재입력 |
| 이미 종료된 경매 | 409 | 종료 상태와 결과 페이지 안내 |
| 동일 idempotency key 재요청 | 기존 결과 | 새 Bid를 생성하지 않음 |

프론트엔드는 금액 입찰을 무조건 자동 반복하지 않는다. 서버 내부의 짧은 재시도 후에도 가격이 변경되었다면 최신 정보를 표시하고 사용자가 다시 판단하게 한다. 네트워크 재전송은 idempotency key가 있을 때만 안전하다.

예시 응답은 다음과 같다.

```json
{
  "code": "AUCTION_CONFLICT",
  "message": "다른 입찰로 현재가가 변경되었습니다.",
  "retryable": true,
  "currentBid": 120000,
  "minimumNextBid": 121000
}
```

## 13. 이벤트 발행 원칙

### 13.1 WebSocket

WebSocket은 DB 트랜잭션의 일부가 아니므로 커밋 전에 발행하면 안 된다.

```text
DB 변경 -> 커밋 성공 -> AFTER_COMMIT 이벤트 -> WebSocket 발행
```

실시간 메시지가 유실될 가능성까지 제거하려면 WebSocket도 outbox를 통해 전달하거나, 클라이언트가 재연결·주기 조회로 최종 상태를 보정하도록 한다.

### 13.2 Kafka

경매 종료 Kafka 이벤트는 기존 Transactional Outbox 방식을 유지한다. 같은 DB 트랜잭션에서 Auction 종료와 Outbox 저장을 함께 처리하고 별도 발행기가 전달한다.

### 13.3 Redis

Redis 갱신을 DB 트랜잭션 안에서 먼저 수행하면 DB 롤백 후 값이 남을 수 있다. Redis를 파생 캐시로 정의하고 다음 중 하나를 적용한다.

- DB 커밋 후 Redis 갱신
- 실패 시 재시도 이벤트 발행
- 주기적인 DB-Redis 정합성 복구 작업

## 14. 테스트 계획

### 14.1 통합 테스트

H2가 아닌 실제 PostgreSQL 환경에서 서로 다른 트랜잭션 두 개 이상을 사용한다.

| 테스트 | 검증 결과 |
|---|---|
| 같은 경매에 두 사용자가 동시 입찰 | 한 요청씩 최신가 기준으로 확정되고 유실 갱신 없음 |
| 같은 금액 동시 입찰 | 정의한 순서에 따라 한 건만 승인 |
| 입찰과 판매자 종료 동시 실행 | 입찰 또는 종료 중 먼저 확정된 한 순서만 반영 |
| 입찰과 스케줄러 종료 동시 실행 | 종료 후 입찰 없음, 낙찰자와 마지막 승인 Bid 일치 |
| 종료 시각 직전/직후 입찰 | 서버/DB 기준 종료 시각 정책과 일치 |
| 관심 등록과 입찰 동시 실행 | 가격 충돌 없이 관심 수도 보존 |
| 낙관적 충돌 재시도 | 새 트랜잭션에서 재조회·재검증 |
| 재시도 한도 초과 | 409와 최신 가격 반환 |
| 트랜잭션 롤백 | WebSocket과 Kafka에 확정 메시지 없음 |
| 같은 idempotency key 반복 | Bid 한 건만 존재 |

### 14.2 AWS k6 테스트

기존 `k6-tests` Auction 계획에 다음 메트릭을 추가한다.

- 입찰 성공 수와 업무 거절 수
- `optimistic_lock_conflict_total`
- `pessimistic_lock_timeout_total`
- 시도별 `bid_retry_count`
- 입찰 API p50, p95, p99
- DB 트랜잭션 시간과 커넥션 풀 대기
- Auction별 최대 동시 요청 수
- WebSocket 수신 값과 DB 최종 값 불일치 수
- Auction 현재가·입찰자·입찰 수와 Bid 집계 불일치 수

동일 총 요청량이라도 분산 부하와 핫스팟 부하를 분리한다.

1. 여러 Auction에 균등 분산
2. 요청의 80~100%를 한 Auction에 집중
3. 종료 10초 전부터 입찰 집중
4. Auction Pod 1개와 여러 개 비교
5. NAS PostgreSQL 네트워크 지연이 있는 조건 비교

## 15. 배포와 롤백

낙관적 락을 도입한다면 다음 순서를 따른다.

1. 기존 행을 포함해 `version BIGINT NOT NULL DEFAULT 0` 컬럼을 먼저 추가한다.
2. 구버전 애플리케이션과 스키마의 호환성을 확인한다.
3. version을 사용하는 애플리케이션을 배포한다.
4. 충돌률, 재시도 수, p95/p99 지연을 관찰한다.
5. 문제가 있으면 애플리케이션만 이전 방식으로 롤백한다.

version 컬럼은 애플리케이션 롤백 후에도 무해하므로 안정화 기간에는 삭제하지 않는다.

## 16. 결정이 필요한 항목

- [ ] 입찰 확정 순서를 DB 잠금 획득 순서로 정의할지 합의
- [ ] 종료 시각 판정을 애플리케이션 시각과 DB 시각 중 무엇으로 통일할지 결정
- [ ] 비관적 락 대기 제한과 오류 응답 코드 결정
- [ ] 관심 수 저장소와 Auction 행 분리 방식 결정
- [ ] 입찰 idempotency key의 생성 주체와 보관 기간 결정
- [ ] WebSocket `AFTER_COMMIT` 구현 방식 결정
- [ ] k6 충돌률 기준값을 AWS 실측 후 확정
- [ ] 낙관적 락 또는 조건부 UPDATE 전환 여부 최종 결정

## 17. 최종 제안

현재 Auction에는 이미 비관적 락이 적용되어 있고, 경매는 종료 직전 특정 행에 쓰기가 집중되는 특성이 있다. 따라서 `@Version`을 바로 추가하고 모든 충돌을 재시도하는 것보다 다음 순서가 위험이 낮다.

```text
비관적 락 적용 경로 통일
  -> 종료 시각과 커밋 후 이벤트 보완
  -> watcherCount 분리와 멱등성 추가
  -> AWS k6로 충돌률과 지연 측정
  -> 낮은 경합이면 낙관적 락
  -> 높은 경합이면 조건부 UPDATE 또는 비관적 락 유지
  -> 처리량이 DB 한계를 넘으면 경매별 큐 검토
```

낙관적 락을 선택할 경우 핵심은 `@Version` 자체가 아니라 **충돌 후 새로운 트랜잭션에서 전체 입찰 절차를 다시 검증하는 것**이다. 어떤 방식을 선택하더라도 DB 커밋과 외부 메시지의 순서, 종료와 입찰의 동일한 동시성 규칙, 요청 멱등성이 함께 설계되어야 한다.
